# Build and contribution guide

## Canonical source layout

Keep game package contents under `Mod/`. Runtime partials stay in `Mod/Data/Scripts/HoloMap/`; the build compiles that directory as C# 6 against installed game assemblies. The implementation namespace is retained for compatibility and is not the public mod interface.

Flat `Examples/*.cs` are PB sources explicitly checked/generated by the harness. General consumer mods belong in `Examples/Mods/`, with wrappers in `Api/Mods/`. New PB helpers belong in `Api/Ingame/`; keep old `Api/HoloMapApi.cs` and portal helper paths compatible.

Public documentation belongs in `docs/wiki/`; SVG diagrams in `docs/wiki/diagrams/` are editable vector source, contain accessible titles/descriptions and use no remote assets. Historical notes belong in `CHANGELOG.md`, not the quick-start README.

## GitHub wiki

The [public wiki](https://github.com/PommesMitChips/HDR-API/wiki) is generated from the maintained documentation. Run the [wiki preparation tool](../Tools/PrepareGitHubWiki.py) with Python 3.10 or later:

```powershell
python Tools/PrepareGitHubWiki.py
python Tools/PrepareGitHubWiki.py --validate-only
```

It writes pages, navigation and standalone SVG assets to the ignored `artifacts/github-wiki/generated` directory. It converts page links and source/example links for GitHub, validates anchors and diagram namespaces, and reports repository upload dependencies. It does not access GitHub or push changes.

Publish by copying the generated contents into a separate clone of `https://github.com/PommesMitChips/HDR-API.wiki.git`, inspecting the diff, committing and pushing the wiki's default branch. Publish the linked source files on repository `main` as well. Update the documented release tuple and pass matching `--release`, `--scene-protocol` and `--client-renderer` arguments when preparing documentation for a new release. Keep unfinished features clearly marked in development.

## Prerequisites and mod checks

- Installed Space Engineers game assemblies.
- .NET 10 SDK for developer checks.
- Node.js for SVG authoring/export steps in the root build.
- Pulsar's matching Harmony/runtime libraries for optional plugin builds and renderer ABI tests.

```powershell
.\Build.ps1
dotnet run --project Tools/Checks/Checks.csproj -c Release -- .
```

Use `-GameBin` on `Build.ps1` or `-p:GameBin=...` on configured projects when the Steam library differs. `Directory.Build.props` supplies default game and Harmony paths; pass `-p:HarmonyPath=...` for a different loader library. Native runtime fixtures currently assume the standard installed game content path unless their runner accepts another location. The checks compile game source and generated PB/mod examples, run geometry/provider/API regressions and exercise the installed PB memory-safe rewrite. The runtime mod is compiled by the game; it does not require a player's .NET 10 SDK.

## Optional native renderer

```powershell
.\OptionalPlugins\HDRClientRenderer\Build.ps1 -Runtime Interim
.\OptionalPlugins\HDRClientRenderer\Build.ps1 -Runtime Legacy
dotnet run --project OptionalPlugins/HDRClientRenderer/Tests/Tests.csproj -c Release
dotnet run --project OptionalPlugins/HDRClientRenderer/PortalMappingTests/PortalMappingTests.csproj -c Release
dotnet run --project OptionalPlugins/HDRClientRenderer/PortalTests/PortalTests.csproj -c Release
dotnet run --project OptionalPlugins/HDRClientRenderer/Tests/Interop/Interop.csproj -c Release
```

Use the runtime matching the user's loader. Native ABI fixtures validate the actual installed engine; they intercept GPU work or use CPU-only vtables. They do not certify real camera pixels, driver behavior or scene performance. See the [client renderer guide](../OptionalPlugins/HDRClientRenderer/README.md).

Serialize builds/runs targeting the same output directory. Independent projects or isolated output directories can run in parallel. Avoid locked apphosts and mixed candidate DLLs during release validation.

## API changes

- Preserve existing PB/source/backend signatures and protobuf tags unless commissioning an explicit compatibility change.
- Add optional capability queries independently from product patch versions.
- Keep PB access checks and server declarations distinct from local viewer/plugin availability.
- Missing optional plugins must not allocate/call their native paths; return status and bounded `Requires plugin…` diagnostics.
- Copy/validate geometry, bound CPU/native submissions and preserve prior valid content on failed replacements.
- Local mod IDs provide lifecycle ownership, not security against trusted installed mods. Require calls on the documented thread; do not imply hidden marshalling or cursor capture.
- Preserve primitive/material/frame lease generations through refresh, resize, failure and late cleanup.

## Output and installation hygiene

`artifacts/`, `bin/` and `obj/` are ignored at every project depth. Keep current release packages, generated demos, validation receipts and recent rollback backups available locally. Archive old investigation builds outside the repo with a manifest; do not erase useful diagnostics or uncommitted source.

[InstallClientPlugins.ps1](../Tools/InstallClientPlugins.ps1) refuses loaded game/loader processes, verifies physical Windows paths and hashes, and preserves Pulsar profile content. Installation is separate from compilation. Recovery helpers for individual development machines are kept with local diagnostics and are not routine installation steps.

`InstallClientPlugins.ps1 -ModOnly` installs mod source for the next world reload without writing plugin DLLs. With a running game it permits changed C# source/metadata only, skips identical assets and requires closure before changing any other mod asset. Use `-InspectOnly` for a read-only plan. Normal plugin installation retains its closed-process guard.

`Tools/Prototypes/UiFocus.cs` is experimental investigation source; it is not automatically part of the game package. Preserve font/vendor licenses and origin notices when reorganizing optional integrations.
