# Optional HDR client renderer

This is an alpha development tree. HDR API **0.9.9 / scene protocol 19** pairs with Client Renderer **0.9.13**, adding optional scoped mouse interaction for retained controls. Use enters the original world-space UI, mouse-up ends a drag, and Escape or context loss exits. Cooperative mod input remains plugin-free. Offline builds and checks do not establish live GPU, native input or multiplayer acceptance.

Client **0.9.12** moves portal capture before the primary scene's culling and drawing. Paired differential planes sample their cropped native capture directly through a private billboard pixel shader, with image and projection data retained together. This removes the full-pane intermediate that spent close-up resolution on offscreen areas. The native capture ceiling remains 2048 per axis; curved and nonlinear portals retain their composed-image path. Ordinary camera panoramas retain their existing capture timing.

Scheduling follows render frames with an anchored requested cadence; game-thread declarations and bounded authorization remain separate. Resolution follows projected pixel density at the physical presentation size and client budgets through stable 256/512/1024/2048 texture buckets. The internal dynamic-resolution viewport remains part of the native projection proof, rather than standing in for the physical display size. A held image between requested capture ticks still represents its earlier eye position; setting a requested rate below the primary frame rate can retain translational parallax during movement. Use the existing demo's `rate 120` command to request up to 120 captures per second; actual capture cadence cannot exceed rendered primary frames and available GPU work. Status capture age describes the captured view, not measured presentation latency.

The updated portal demo defaults to `size native` and 60 Hz requested. Use `size 1024` to set a ceiling or `rate 1..120` to adjust cadence. Server declarations can request up to 4096 per axis; actual detail reflects validated native limits and the local budget. New bucket fronts are single-mip and retain their live SRVs. Active UV regions stay fixed for each retained lease.

Startup uses a bounded protected local shader cache tied to frozen expanded source and compiler/runtime identities. Cache hits still undergo reflection/ABI checks. Two background CPU jobs compile sealed variants; engine preprocessing and GPU attachment stay on their owning threads. Atmospheric scattering starts beyond the shell crossing, and clouds use geometric cutoff. Live visual, cadence and cold/warm startup validation remain pending.

Client **0.9.10** fixes the portal front-texture retirement path implicated in the primary billboard batch crash after distance/visibility changes. Its two registered front bindings retain fixed 512-square resources and become transparent when the source is retired. Private capture and staging buffers remain disposable; logical portal resolution still controls ray-packet detail. Composition and pixel accounting use the physical target dimensions. Engine manager ownership keeps old queued billboard references valid across demand drops and renderer backend reloads. Live crash verification remains pending.

Paired planar portals evaluate their affine ray mapping in the GPU compositor; nonlinear surfaces retain dense CPU ray packets. The source capture is **1024×1024**, up from 512×512, and physical pixel accounting includes that capture plus the fixed 512-square composition target. The portal demo now requests **512×512 at 30 Hz**, up from 256×256 at 6 Hz. Use PB arguments `size 64..512` and `rate 1..30` to adjust it. These are requested settings; actual cadence depends on capture, ray generation and the client frame rate. PB Update100 only maintains the declaration, while the optional client performs captures.

This prevents the mod from clearing its cached display between captures and its slower source acquisition. Each successful commit updates an immutable publication snapshot with the current pixel generation, viewer pose and coverage. Configuration changes, authorization loss, device resets, cancellation and failed front copies still revoke the lease. HDR API 0.9.5 avoids duplicate lease release during failed acquisition cleanup; hard render-budget failures still clear the cached view. Protocol 17 and the current portal script remain compatible. Offline retention and lifecycle tests pass; live flicker validation remains pending.

Small native draw wrappers can be inlined before later detours become visible. Portal certification now guards the audited renderer call sites directly and preserves the exact-one draw requirement. Compiled-path tests exercise all six actual unmanaged draw paths using CPU vtable stubs, precompiled nested Stereo callers, and later Harmony patch/unpatch. They perform no GPU draw.

Client **0.9.7**, with HDR API **0.9.4 / protocol 17**, adds native occlusion and portal providers. `/hdr camera occlusion on|off` selects display suppression locally (default off). Current primary opaque depth, all MSAA samples, complete static consumer enclosures and matching publication identities are required. The query is nonblocking; pending results keep demand, so savings depend on GPU readiness. Moving anchors, unknown/mesh/LCD consumers, near crossings and geometry outside the conservative domain fail open. Historical enclosures never shrink during a world lifetime.

`native-portal` accepts bounded numeric declarations. Try `artifacts/PortalDemo.pb.cs`: `plane`, `ellipsoid`, `mesh` and `stealth` select the supported mappings. Captures occur after the primary scene returns, using private buffers/context state and guarded world shaders on audited immediate/deferred/native draw boundaries. Shader variants warm on demand; unknown coverage rejects the frame. This geometry-only shell omits atmosphere/cloud volumes, debug primitives and custom-projection billboards; existing shadow lighting is retained. The lightweight ordinary-camera profile remains a separate optional setting.

Portal output uses fixed materials `HDR_ClientPortal_0/_1`, owned front/staging targets, stable resource-lease eligibility generations, immutable per-publication pixel stamps and resource-epoch checks, renewed game-thread authorization and serialized render-thread retirement. Failed staging work retains the prior front; failed front publication invalidates evidence. World departure drops declarations. The shared pixel allocator charges capture plus composition base pixels; scene shading, uploads, mips and publication copies cost more. Nonlinear strict mappings can have sparse transparent coverage; explicit approximate shell sampling has parallax limits. A narrow band outside the authored shell may also disappear. `/hdr portal status` reports local readiness/failures. Install all 36 static materials with the world mod. Client **0.9.6** replaces fixed quadrants with a density-gradient/benefit quadtree on the existing 16×16 source-UV map. It looks ahead through heterogeneous regions, preserving conservative coverage and density bounds. The bounded heuristic is not a globally optimal tile allocation under tight limits. Uniform fields coalesce without constructing the full tree. Default settings allow 16 leaves and charge 16,384 pixel equivalents per extra scene pass; `/hdr camera tiles 1..64` and `/hdr camera tile-cost N` adjust this locally. Zero tile-cost favours raster savings over pass overhead. `/hdr camera adaptive off` retains one uniform image. Image cadence still applies to batch starts, and native pass/pixel limits remain separately configurable.

The compositor uses a 16×16 leaf-index table rather than a per-pixel scan of up to 64 regions. Grid-aligned leaves take constant-time lookup; arbitrary non-grid rectangles retain bounded fallback scans. Exact sparse footprint edges preserve their last texel. The six-face fixed constant layout is 18,832 bytes, verified against the installed D3D compiler and mapping ABI. Full image batches keep one optical pose and publish only when all tiles finish. Warm/hidden sources pause continuation work. Tightening a pixel budget discards staging and replans while retaining the complete front. Per-crop postprocessing and mixed-resolution edge filtering still need in-game visual checks; reduced pixel counts do not imply negligible scene-pass cost.

The components introduced during 0.9.6 are connected by the 0.9.7 adapters above. No player occlusion arrays or main renderer shader dictionaries are replaced.

The v13 camera PB demo accepts finite positive rates including `rate 60` and `rate 144`; all world-mod peers need 0.9.1 / protocol16. Rates are requests, not throughput guarantees. Existing general surfaces are unchanged.

Use HDR API 0.9.0 / protocol 15 and Direct Camera Sphere v12. Normal capture quality remains the default; use `quality lite` to opt in. General ellipsoid and UV-mesh surfaces are implemented by the world mod's local renderer.

That budget uses the internal dynamic-resolution viewport; portal detail planning separately uses physical presentation dimensions. Clears, mips and bandwidth are secondary diagnostics. All tiles use a frozen optical pose, and publication waits for the completed atlas. Actual image cadence can be lower than the requested 30 Hz. Missing or stale density falls back conservatively to a whole forward view.

Version **0.8.0** adds the `camera-panorama` display provider. An HDR projected screen selects one to six physical camera block entity IDs directly; the plugin captures them into its own bounded native render targets, then composites them into one equirectangular GPU texture. This mode requires HDR API **0.8.0 / protocol 14** and its two `HDR_ClientPanorama_0` / `_1` material definitions. It requires no CameraLCD plugin, LCD block, LCD texture, 360 capture plugin or server video stream. Existing `lcd-texture` and raster UI services remain available.

Client **0.8.1** repairs a texture-allocation overread found in the 2026-10-05 crash. The installed engine's generated-texture reset constructs initial-data pointers for every mip level. Supplying only the base RGBA level is therefore unsafe when mipmaps are enabled: a 1024-square texture needs 5,592,404 initial bytes, while 0.8.0 supplied 4,194,304. Camera, panorama and LCD-relay targets now allocate without CPU initial pixels and are cleared on the GPU. Raster UI uploads remain single-mip. The client also replaces generic by-reference Harmony prefixes that failed on actual invocation, and suppresses CameraLCD's extra captures only while HDR's native capture state is active. Normal CameraLCD main-view operation is preserved.

The crash was located by the Windows .NET Runtime event's stack through `DirectCameraCaptureNative.CreateTarget` and `SharpDX.Direct3D11.Texture2D` construction. Offline checks reproduce the allocation contract and execute the actual managed detours; they still do not execute a GPU frame. Bounded, flushed first-attempt markers identify allocation, capture, state restoration and composition if another failure occurs. The 0.8.x world mod used **0.8.0** and **Direct Camera Sphere v11**.

The source ID is a comma-separated list of one to six distinct positive camera entity IDs, at most 256 characters. The `frame` ABI keeps the standard 14 arguments and optional output width/height at positions 15/16. Its kind-2 response carries `MyTuple<string,Vector2I,long>(materialName,outputSize,generation)` and opaque validity evidence. `source-state` uses the exact `camera-panorama` source ID. The local HDR service query `source-panoramasettings` takes `{ "camera-panorama", anchorId, callerId, sourceId }` and returns `MyTuple<double,double,double,int>(FOVDegrees,featherDegrees,saturation,captureResolution)`. Defaults are **105°, 8°, 1.15, 1024**; limits are FOV 60–120°, feather 0–25°, saturation 0–2, and native capture resolution 256, 512 or 1024.

The existing `source-demand` query also bounds capture cadence and resolution. Its visible source dimensions and rate are unioned across consumers, paced at the requested rate or a configured local ceiling, and bounded by the source's configured camera resolution. A small or distant panorama's effective dimensions reduce whole-camera capture sizes. The `source-cameradensity` request adds an 11-double basis per CSV camera (`Rxyz,Uxyz,Fxyz,tanHorizontal,tanVertical`), and accepts `MyTuple<int,double[],bool>(visibleMask,packed,currentGeometryKnown)`. The packet header is `{16,cameraCount}`, followed by suggested camera sizes and 256 seven-value cells per camera: `{Covered,UpperMagnification,UpperArea,Magnification,Area,BlendWeight,HasSample}`. Malformed or unknown packets request all cameras conservatively.

The current cheap visibility mask controls intentional camera omission. Hidden cameras stop capturing and retain their last valid texture for a short native warm delay; consumer masks are unioned, so one hidden or released screen cannot pause a camera still needed by another. Newly demanded cameras warm while a still-valid previous composite remains available. Current geometry proof does not mean fresh local density: `HasSample=false` conservative fields retain established resolution rather than causing repeated resizing. Sustained lower fresh demand shrinks after two seconds; higher fresh demand and higher whole-screen occupation grow promptly. The density grid drives independently sized native crops; whole-camera ceilings and local leaf/pass-cost settings still bound the plan.

Native capture is limited to six reused camera targets, three captures per actual main render frame and 30 Hz per source. It takes each pose from the physical camera's optical dummy, checks actual color/depth attachment dimensions and bounds its capture target accordingly. The compositor runs later in the same main-frame hook, rereads each latest completed capture pose, and derives the pinhole projection from that pose and the queued anchor orientation. Its axes match HDR's angular sphere: panorama UV centre points toward anchor-local +Z, U increases toward +X, and V decreases toward +Y. Camera motion never pairs newly captured pixels with an older pose merely because a target name was reused.

The compositor's single fixed embedded `ps_5_0` shader samples at most six trusted native textures at LOD zero. It computes inverse pinhole UVs, feathers camera edges by angular distance and normalizes overlap weights in linear RGB. It ignores the source alpha and produces alpha one wherever covered, with true RGBA-zero gaps elsewhere. Saturation is applied after the normalized blend using Rec.709 luminance. Sources and target use the engine's sRGB texture formats, so sampling/output perform the color-space conversion; there is no manual gamma correction. Screen, side and layer opacity remain final HDR presentation controls.

Panorama output is bounded to **2048 × 1024 / 2,097,152 pixels**, with uniform reduction of larger valid requests. Two resident panorama targets reserve at most **32 MiB** conservatively for base pixels and mips. New targets allocate without CPU initial pixels; video refreshes reuse targets and perform no CPU video upload or readback. Composition is capped at two passes and four megapixels of base output per update and per main render frame, plus one bounded mip regeneration per completed output. The installed engine creates a full mipchain when its generated-texture RTV flag is enabled, even if `CreateGeneratedTexture` receives mip count 1; panorama composition and LCD relay now unbind the RTV and regenerate those mips after drawing so distant presentation does not sample old initialization data.

Direct sources are accepted only through the current entity gateway, with live working PB/anchor/camera blocks, same construct, PB-owner access and access for the local player's identity. The local character must be within 60 m of the anchor; remote cameras on that same long ship/station are supported. No arbitrary source pose, caller shader, raw pointer, file path or remote code enters capture or composition. Loss of access, power, exact entity identity, visible demand, verified native generation or compositor health retires cached output and its demand. World/device epochs cancel queued work and retire owned targets. Releasing one panorama screen preserves a peer screen that still needs the same camera.

Both native capture and composition install only after their fixed engine ABI gates pass. Camera billboard isolation installs independently of CameraLCD and excludes HDR fill/line, raster, LCD and panorama materials while the direct capture flag is set. Main-view billboards and unrelated camera-view billboards keep their normal behavior. Capture and compositor hooks use exact backbuffer identity and the engine frame counter; secondary passes cannot spend another main-frame budget. GPU queue acceptance and command submission are not visual acceptance or measured performance.

The plugin registers these local services only after a client world, entity gateway and renderer are present:

* Raster upload service: discovery `481770110` carries HDR's `Func<string,object[],object>` service; registration `481770111` is `MyTuple<int,Func<string,object[],object>>(1,endpoint)`. `caps` returns `MyTuple<int,int,int,int>(2048,2048,1048576,16)`. `upload` takes `{ string key, long serial, int width, int height, byte[] straightRgba }` and returns `MyTuple<string,object>(materialName,opaqueLease)` on success, or null on invalid or busy work. `valid` and `release` take `{ lease }` and return bool. Each key needs an increasing serial to change. The plugin copies straight RGBA, premultiplies RGB in linear light, then re-encodes sRGB bytes to match the renderer's premultiplied billboard blend. Public `MyRenderProxy.CreateGeneratedTexture`, `ResetGeneratedTexture`, and `DestroyGeneratedTexture` queue work on the fixed `HDR_ClientRaster_N` targets. Sixteen resident slots hold at most 16 MiB; uploads are capped at 4 MiB per update. No CPU readback occurs.
* LCD display provider: discovery `481770100` carries HDR's service; registration `481770101` is `MyTuple<string,int,Func<string,object[],object>>(lcd-texture,2,endpoint)`. Source IDs are `lcdEntityId:surfaceIndex` (up to 64 characters). `frame` accepts the 14 standard source fields, plus optional output width and height at fields 15 and 16; legacy 14-field requests use 256 × 144. Output dimensions are 16–1024 each and at most 262,144 pixels. Each accepted frame queues a direct render-thread RGB copy from the existing LCD offscreen texture to an owned fixed `HDR_ClientLcd_N` generated target; the source texture is never destroyed by this plugin. The response is `MyTuple<int,object,object,bool,double>` with kind 2, payload `MyTuple<string,Vector2I,long>(materialName,outputSize,generation)`, opaque validity evidence, `false`, and requested refresh cap 60 Hz. HDR's screen setting controls the actual cadence. Copies are limited to 2 MiB of output pixels and four frames per plugin update. Sixteen LCD targets hold at most 16 MiB of RGBA data.

The LCD `valid` command checks the exact live source entity and surface, generated source texture name and native size, active HDR source declaration, anchor and caller PB, power, same construct, owner access, and a local character within 60 m of the anchor. `release` accepts `{ evidence }`. Each HDR screen has its own target lease, even if another screen uses the same LCD and output size. HDR releases that evidence when detaching or resizing the screen; releasing one screen cannot destroy its peer's target. Removing, switching, resizing, or revoking a source retires its owned target and evidence. This compatibility provider only copies the already rendered LCD image; the separate `camera-panorama` provider captures physical cameras directly. `CanCapture` is true only when registration, native capture, capture isolation and client readiness gates all pass.

All endpoints require the plugin update thread. The raster service can register once a client session, entity gateway and renderer exist; the LCD source authorization additionally requires a live local character. World leave, plugin disposal, render-thread or device-settings change, and a client host call to `SignalDeviceReset()` retire leases and queue destruction of owned targets. Public APIs expose no reliable callback for a reset that retains the same thread and settings; the host must signal that case. Renderer queue acceptance is not GPU completion. The fixed-material GPU copy path, alpha result, UV orientation, world reload, device reset, and multiplayer permission changes require an in-game client acceptance test; none was run here. Activation transitions and the first failing gate are logged with an `[HDRClientRenderer]` prefix in the normal game log, at most 32 times per plugin instance.

`dotnet run --project Tests/Tests.csproj` exercises the independent raster budget, LCD source/target lease policies and capture-list isolation with fake backends. `dotnet run --project Tests/Interop/Interop.csproj` validates installation/removal of the Harmony isolation patch against the actual read-only game renderer without drawing a frame. `Build.ps1` compiles C# 7.3 for .NET Framework or .NET 10 against read-only installed DLLs. It expects Pulsar's matching Harmony library; the .NET 10 project accepts a `HarmonyPath` override.

Capture isolation patches the two transient billboard-list reads in `MyBillboardRenderer.PrepareList` independently of CameraLCD. During direct HDR capture or the optional `CameraLCD.CameraViewRenderer.IsDrawing` scope, HDR's fill/line and fixed raster/LCD/panorama billboard materials are filtered from a separate list. Player-view inputs and unrelated billboard materials remain unchanged. The patch prevents HDR self-capture and isolates the extra camera pass from HDR surfaces. The managed October 4 crash occurred in that extra pass's billboard gathering; this mitigation needs in-game verification. HDR surfaces still use textured billboard triangles, not a dedicated textured-mesh backend.

LCD relay copies clear their destination to opaque black before the engine's texture copy pass. CameraLCD writes camera RGB with zero alpha for native LCD use; copying that alpha directly into a hologram would make the feed invisible. This normalizes the LCD image's alpha without reading it back to CPU. Screen/side/layer opacity still applies at presentation; UI raster uploads continue preserving their own transparency. Actual camera pixels and GPU blending still require in-game acceptance.
